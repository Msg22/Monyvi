## 1. Verified carrier defect: opted-in old-server v1 loses its original financial provenance

The actual [`parseAiResponse` v1 branch](https://github.com/Msg22/Monyvi/blob/a8a1e58108f9ecae9bd0cd2ae6e3aed7d49dd452/apps/mobile/services/ai-sms-parser-response.ts#L142-L223) retains original **strict-v1** `AiSmsTransaction` (including `messageId,date,categorySystemName,isTrusted,currency`) and maps it to `ParsedSmsTransaction`; it does not populate `reviewV2FinancialRows` or `reviewV2ProviderResponse`. [`reviewChunkFor`](https://github.com/Msg22/Monyvi/blob/a8a1e58108f9ecae9bd0cd2ae6e3aed7d49dd452/apps/mobile/services/ai-sms-chunk-runner-service.ts#L591-L615) currently requires **both** v2 carrier fields, so *every opted-in original request answered by a true untagged v1 server* produces **no `reviewChunks` at all**, even when its financial transactions were valid, source-correlated and mapped. [`resultFromState`](https://github.com/Msg22/Monyvi/blob/a8a1e58108f9ecae9bd0cd2ae6e3aed7d49dd452/apps/mobile/services/ai-sms-parser-service.ts#L256-L277) therefore cannot supply T014-M's raw financial rows. Rebuilding them from mapped finance would lose the original date string, original `categorySystemName`, nullable-v2 distinction and per-message source identity; **do not** reverse-engineer `financialRows` from the display/domain DTO.

**Chosen compatible correction (Core parser lease, only after Root tests-first approval):** carry the original validated *strict-v1* financial rows **before mapping** into the **same opt-in-only** canonical `SmsReviewChunk` shape as v2. Use the already authoritative `accountReviewSmsFinancialRowSchema.safeParse` for the T014-P-compatible financial projection (no copied DTO, category ID synthesis, timezone conversion or preferred-currency provenance). Retain original `messageId,date,categorySystemName,amount,type,currency,isTrusted,ATM/card` and the admitted message's exact `id,smsFingerprint,body,sender`. Set **`providerResponse:null`** for genuine **missing** version, never `{reviewContractVersion:"account-review/v2",...}`, `currencyEvidence:"omitted"`, `accountEvidence:"absent"` or accepted accountId. Any legacy financial date outside canonical source-date contract remains a *bounded unrepresentable review-row/error case*: keep its existing parsed financial behavior, return recoverable unresolved review status and do **not** alter the historical date by `Date.toISOString()` or fabricate a canonical input. Root should add its real date-only/ISO/offset regression here. No-opt-in, QA, live/headless and empty transport must not start a review session.

## 2. One owned local queue namespace — never transport IDs as session UUIDs

Current [`SmsAiRequestContext`](https://github.com/Msg22/Monyvi/blob/a8a1e58108f9ecae9bd0cd2ae6e3aed7d49dd452/apps/mobile/services/ai-sms-parser-service.ts#L103-L112) has `scanSessionId:string|null` and `scanStartedAtMs?`; chunk [`requestKey`](https://github.com/Msg22/Monyvi/blob/a8a1e58108f9ecae9bd0cd2ae6e3aed7d49dd452/apps/mobile/services/ai-sms-chunk-runner-service.ts#L492-L530) may regenerate on 413 splits and fresh retries. Neither is a trustworthy **`AccountReviewSession.sessionId` UUID** or group/row identity. Local `SmsScanContext.reviewSessionId` is a **number**, also not a UUID. Source rows retain `messageId + smsFingerprint`, and the published pure T014-P normalizer derives stable row/group UUIDs from owner/session/source/evidence; it must never use request transport aliases to dedup or rebind a user choice.

**Namespace allocation authority:** NormalSQL T014-M owns a *single canonical local* `sessionId:AccountReviewSession["sessionId"]` minted **once for one interactive owner's first complete review session**, not once per transport chunk. Reuse an existing approved local queue session ID when one already exists for that same owner/queue/source epoch; otherwise create one fresh canonical UUID using the already approved native `Crypto.randomUUID()` (or hashed UUIDv8 with a separately approved stable queue lineage, not raw `scanSessionId`). Keep it in the scoped completion/queue operation until final publication. Root must freeze the exact queue lineage provider before source; **do not** derive from the user-visible numeric `reviewSessionId`, silently cast `scanSessionId`, or use `ChunkWork.requestKey` as `sessionId`. If no active interactive queue identity exists (live/headless/QA), preserve the old parser result with no group session.

**Alias namespacing:** Because `transactionRef`/`suggestionRef` are **provider-local aliases**, multiple valid chunks may independently use `"tx-1"`/`"group-1"`. T014-M's first-session assembler assigns a non-PII local namespace per **accepted** chunk (e.g. length-delimited chunk request key plus admitted-source ID scope) to the model aliases and matching `suggestedAccounts[].transactionRefs` **together**. Preserve the original SMS evidence spans' `sourceRef = submitted messageId`, and never prefix original fingerprints, message IDs or raw body/sender. If two attempts produced one accepted fingerprint, use only one grounded original financial entry; conflicting duplicate outcomes fail closed/unresolved, never select a winner by arrival order. Equivalent **canonical evidenceKey** can still group compatible messages across chunks irrespective of model alias or transport ordering; incompatible card/type/provider/currency evidence never merges.

This is a **local-source adapter**, not a copied provider/financial DTO; `SmsReviewChunk` is the existing canonical `Pick<SmsReviewNormalizationInput>`. It may call pure `normalizeAccountReviewParserResult` **per accepted source chunk using the same pinned sessionId, owner and original requestKey**, then combine **only initial, unselected, unconfirmed pending** rows/groups using stable row/group IDs and canonical evidence keys. Do not funnel all rows through a single synthetic v2 envelope: mixing genuine v1/no-advisory with valid v2 can wrongly promote v1 into hard-invalid-advisory, while setting all provider responses null discards good v2 evidence. No re-parsing an AI model and no second provider/grouping call.

Group merge across normalized chunk snapshots requires matching `groupId,evidenceKey,type,currency,provider/card/institution`, unions matching `linkedRowIds` and **namespaced** suggestion refs, and keeps groups **pending**; ambiguous/contradictory evidence remains unresolved rather than retroactively selecting/confirming anything. Validation via `accountReviewSessionSchema` must succeed for the *whole combined session*, with original row `reviewReasons`, `currency`, source/destination proof, revision 0, selected false and saveIntent null retained. Return a *new* result; original `transactions`, hashes, metadata, fingerprint completions, retry guidance and flow status unchanged. The existing one-input `createSmsAccountReviewSession(SmsReviewNormalizationInput)` remains available and unchanged for bounded tests/callers.

**Core-owned invocation once per complete original result:** after `runConcurrentChunks`/sequential finalization (not from `onProgress` or `applyChunkResolution`), `parseSmsWithAi` calls the **actual** SQL-owned `createCompleteSmsAccountReviewSession` directly when `context.reviewAccountSnapshots` exists and the request is interactive/admitted; the Core parser need not import back from the adapter through a parser cycle—the adapter currently imports only pure logic, T010, auth. Attach via the already exported pure `attachSmsReviewSession`, preserving the existing `AiParseResult` optional shape, matching current owner and the pinned namespace. **No new public required callback, session factory, constructor, new parser arguments or hook/DB query.** A failed owner/cancel/adapter finalization never publishes a fabricated session or pretends v1 omission; it gives a recoverable review failure without another DeepInfra call or losing the original validated finance in the source result.

**Hybrid/local final publication:** SQL T014-M owns review-only changes to `sms-parser-orchestrator.ts`/trusted-local adaptation, matching the same owned queue namespace from the internally received AI result or a SQL-owned local allocator if there were no AI positives. It composes the final selected **admitted source set** after the existing trusted+AI dedup and supplies deterministic locally grounded evidence only where proven; otherwise `providerResponse:null`/unconfirmed. **No intermediate AI-only or per-chunk `reviewSession` may be emitted through incremental progress/UI**; only a fully assembled final review session for that source set. Direct `parseSmsWithAi` callers still receive the full initial accepted-AI session on completion. Subsequent late arrivals **after user edits**, tombstones, selection or confirmed groups require the separately owned T027 conflict-aware reducer and must not replace a current session with a new initial snapshot.
