## Recommended frozen guard: exact current-state CAS

**Use the lead's current-state contract, not a monotonic metadata revision:**

```ts
interface DefaultAccountStateGuard {
  readonly expectedActiveOwnedAccountIds: readonly string[]; // sorted canonical UUIDs
  readonly expectedDefaultAccount:
    | { readonly accountId: string; readonly isDefault: true }
    | null;
}
```

- The expected state is **all active owned account UUIDs in canonical sorted order**, plus exactly one active owned default with `isDefault: true` or `null`. Compare the complete state atomically against the server state; verify UUID format/order/uniqueness, user scope and non-deleted status. No count-only or timestamp-only proxy. A locally inconsistent multiple-default snapshot must fail closed.
- The lead explicitly permits identical **A→B→A** states: after this sequence, a guard expecting A may succeed because current observable state again equals A. Do **not** introduce a monotonic `default_revision` solely to reject that case. The prior provisional revision recommendation is superseded by this direction.
- First account remains default; later explicit OFF preserves current default or no-default; later explicit ON clears **only the prior default's flag** and sets the new account as default. Cancel/failure changes nothing. Group confirmation does not create or set a default. Preserve the existing at-most-one partial index and account/child/opening-balance rules from [account-default-intent contract](https://github.com/Msg22/Monyvi/blob/944cbafc7e7d9f36a13c75d20c0669204974db2/specs/395-shared-account-review/contracts/account-default-intent.md#L9-L50).
- Freeze one stable `actionId`, hash, created account/child IDs, and guard in the local action. The **expected canonical server state** must be distinguished from unsynced optimistic local changes. Locally chained default actions must be pushed sequentially and resolved against their dependency; never rewrite the payload/hash after ambiguous transport success.
- Keep the new strict `accounts/create_with_default/account.create-default/v1` tuple and the strict review batch registration independent of legacy `account.balance-effects/v1`. Zero-opening create and zero-net batches must be valid complete actions with explicit guards, not fabricated nonzero effects. Server check/apply and local reconciliation must preserve at-most-once behavior, ownership and all-or-nothing linked account/child/default/financial outcomes. See [financial-save contract](https://github.com/Msg22/Monyvi/blob/944cbafc7e7d9f36a13c75d20c0669204974db2/specs/395-shared-account-review/contracts/financial-save.md#L91-L132).

## Mandatory lock-order proof gate — technical feasibility

**Every participating server account/default writer must acquire locks in this order: publication fence → per-owner lock → account-row locks (ascending canonical account ID), then check/apply.** Holding only the existing account-row locks is insufficient: an owner currently having *zero* accounts has no row to lock, and a concurrent creation is a phantom relative to the active-ID set. The owner lock must be stable even for the empty set (for example a private per-user lock row initialized safely), and it must be acquired before reading/locking account rows for the state comparison.

- [SQL082 lines 13–41](https://github.com/Msg22/Monyvi/blob/944cbafc7e7d9f36a13c75d20c0669204974db2/supabase/migrations/082_sync_writer_fence_foundation.sql#L13-L41) establishes the publication-fence API; [SQL083 lines 89–173](https://github.com/Msg22/Monyvi/blob/944cbafc7e7d9f36a13c75d20c0669204974db2/supabase/migrations/083_sync_account_early_fence.sql#L89-L173) shows the financial action acquiring the fence before account `FOR UPDATE` locks. New owner locking must fit this order rather than reverse it.
- **Feasibility risk to prove, not silently assume:** current generic account metadata upserts, metadata-only Edit and legacy account creators are not all routed through the new guarded RPC. If an old writer acquires an account row lock first and only later attempts the owner lock via a row trigger, it can violate the required order and deadlock. A trigger-added lock alone does not prove correct ordering. The implementation must inspect every server write entry point and either enforce compliant pre-row lock order (including relevant legacy clients) or explicitly block incompatible generic default/account-membership mutations before enabling the new action. This is a compatibility/protocol safety gate, **not authorization to change product policy or abandon old clients**.
- Protect action-owned account/child/default fields from generic push, and make rejection/restart reconciliation restore linked account/children/default/effects without overwriting newer canonical accepted changes. Any failure in pull/push must propagate; no unsafe generic fallback.
