## Second pass — actionable logic/privacy findings

### P2-01 — Explicit null SMS review version silently enters the v1 path (new Edge request-boundary regression)

**Sources:** `supabase/functions/_shared/sms-ai/sms-ai-request-boundary.ts:69-85,97-129` at Core `180c6368`; governing `contracts/parser-evidence.md:5-10` and `:84-90`.

**Concrete trigger:** send an otherwise valid original parse-sms JSON request containing `"reviewContractVersion":null` **as a present key**, with no `reviewContext`. `reviewContextFrom` assigns `version=null` and accepts the absence of `reviewContext`, then `parseSmsReviewV2Context` returns null, and `parseSmsRequestBody` returns a v1-shaped request. This is not an old client *without* a discriminator; it explicitly supplied an invalid discriminator. The higher-level helper's test for `"account-review/v3"` (`sms-ai-review-v2.test.ts:102-113`) does not exercise this raw boundary.

**Impact:** fail-closed version negotiation is inconsistent with the frozen “only clients without the field keep v1” contract. A malformed/unsupported opt-in can be processed with legacy prompt and currency defaults rather than rejected before policy/quota; normal mobile sends the proper v2 literal, so the production frequency is unverified.

**Recommendation:** in the raw request boundary distinguish *property absent* from *property present with null/unknown value*; reject present-null and unsupported versions before admission. Add an actual `parseSmsRequestBody`/handler regression that checks no quota/provider call for present-null, while true missing key remains v1. **No fix made.**

### P2-02 — Unsupported Voice response version loses the hard invalid-advisory reason (cross-module semantic mismatch)

**Sources:** `apps/mobile/services/ai-voice-parser-review.ts:62-82` and `ai-voice-parser-service.ts:673-701` at Core `180c6368`; `packages/logic/src/account-review/normalization.ts:77-110,146-163,218-224` at normalization `cb50c8d2`; governing `contracts/parser-evidence.md:84-109,127-132`.

**Concrete trigger:** a v2 Voice request receives a financially valid response with a *present* `reviewContractVersion:"account-review/v3"`, otherwise unchanged from valid v2. The mobile classifier correctly calls it `malformed_advisory` and retains raw provenance, but the caller passes only raw `providerResponse` and valid finance to the normalizer, not the classification. `readAdvisory` fails canonical v2 parse, while `isV2Response` returns **false** for anything other than the exact v2 value, setting `isMalformed:false`. The resulting row is unconfirmed/uncertain like an old v1 response but is missing `account_evidence_invalid`, the hard reason required for malformed tagged evidence. By contrast the SMS mobile response boundary rejects a present unknown discriminator (`ai-sms-parser-response.ts:229-241`).

**Impact/limits:** this does **not** authorize auto-selection, confirmation, or Save: row currency/account still remain unresolved, so avoid presenting it as an authorization bypass. It does mask an unsupported version as legacy unknown at the canonical review-reason level, which can mislead review/error handling. Helper test `ai-voice-parser-review.test.ts:168-175` checks only the classifier, not the downstream full session.

**Recommendation:** treat **any present-but-invalid review discriminator** as tagged malformed provenance when computing the hard reason, while preserving true absence as the conservative old-server v1 path and preserving valid financial rows without another provider call. Add a real classifier→original-parser→normalizer review-reason assertion. **No fix made.**

### P2-03 — Semantically invalid Voice transaction diagnostics can log user/provider text (pre-existing path, now reachable by v2)

**Sources:** `apps/mobile/services/ai-voice-parser-service.ts:624-640` at Core `180c6368`, with the same legacy behavior in governing `ai-voice-parser-service.ts:518-529` at `9a8987a8`; governing `contracts/parser-evidence.md:104-109`.

**Concrete trigger:** an opted-in Voice model returns an otherwise well-shaped financial row whose `categorySystemName` fails `parseCategory` (e.g. a user-specific category string). The catch logs `categorySystemNameLength: aiTx.categorySystemName` — **the full value, not its length** — plus `currency` and an arbitrary `error.message`. The data is an untrusted model-supplied string and may contain user-derived category names or spoken fragments. The older v1 code already had this diagnostic; this is **not** a claim that T012 introduced it. It is nevertheless reachable in the approved new review mode and conflicts with the privacy contract's codes/counts-only logs.

**Impact/limits:** potential PII exposure in client logs; where logs travel/are retained was not verified. The newer v2-specific errors use bounded reason codes, but the inherited catch is shared.

**Recommendation:** in a future explicitly owned source correction replace the raw `categorySystemNameLength`/currency/error text with stable reason code, error class and counts (including v1 if approved); assert a synthetic private category marker never reaches `logger.warn/error` for v2 mapping failure. **No fix made.**

### P2-04 — SMS tagged-v2 response missing *all* safeguard metadata is accepted as success (defensive protocol gap; no verified live Edge trigger)

**Sources:** `apps/mobile/services/ai-sms-parser-response.ts:223-259,275-319`; `ai-sms-chunk-runner-service.ts:717-752` and `ai-sms-parser-service.ts:268-283` at Core `180c6368`; governing `contracts/parser-evidence.md:42-54,111-132`.

**Concrete trigger:** feed `parseAiResponse` a syntactically canonical `reviewContractVersion:"account-review/v2"` envelope with one valid correlated SMS financial row out of two submitted originals but omit **all four** `completionStatus`, `negativeFingerprints`, `terminalFingerprints` and `unresolvedFingerprints`. `parseSafeguardMetadata` treats *zero present metadata keys* as `createEmptySafeguardMetadata(false)`. The v2 response schema makes these fields optional; `parseSmsReviewTransport` then returns `hasError:false` with one mapped transaction, and `applyChunkResolution` does not mark the other original as unresolved. This is distinguishable from a legitimate complete response with authoritative negative fingerprints.

**Impact/limits:** the current reviewed Edge handler always constructs these fields in its normal complete/incomplete responses (`parse-sms-handler.ts:495-503,574-588`), so this is **not** a demonstrated normal production path or a claim of lost real data. It is a versioned wire fail-open if a v2 server/proxy regression omits all safeguard metadata, allowing an incomplete chunk to appear complete without an unresolved retry signal; the legacy v1 optional-metadata behavior predates #395.

**Recommendation:** require the source-owned completion/fingerprint envelope for **tagged v2** successful SMS responses, preserving v1 compatibility. If absent, classify as invalid/unresolved (not a fabricated durable negative); test a two-message chunk and ensure no silent omission or additional provider request. **No fix made.**

## Distinct test gaps (recommendations, not additional verified defects)

1. **Boundary/version matrix:** end-to-end raw SMS `parseSmsRequestBody`/Edge refusal for absent, explicit null, v3, malformed context, and no quota/provider on invalid; Voice v3 through actual canonical normalized `reviewReasons` (not just helper `kind`).
2. **Wire completeness/chunk association:** v2 two-message one-positive/one-absent-metadata case, a mixed malformed advisory + valid financial positive with **no durable negative**, and concurrent admitted chunks/reorder proving `messageId + actual fingerprint + requestKey` separation. Existing helper tests cover many of these primitives but do not cover every handler→chunk→session route.
3. **Owner/cancel/hash race:** source-owner switch or abort while a mocked deferred Expo SHA digest or T010 snapshot read is pending; assert no stale `reviewSession` reaches a caller, no second provider request, and no cross-owner attachment. Existing guards look appropriately placed; this is coverage, not a verified flaw.
4. **Diagnostic privacy:** semantically invalid v2 Voice category containing a private marker; assert every error/warn payload omits that marker, original transcript, counterparty, original SMS body/fingerprint, model response and hash input.
5. **Full original provider plan:** handler-level accepted/excluded-candidate execution mock asserting pre-admission token accounting and the **same** post-exclusion messages/schema object reaches the single configured DeepInfra executor. Focused `sms-ai-review-v2.test.ts:115-209` already tests generated plan/estimator; this proposes higher-level coverage, not duplicate unit checks.
6. **Unknown/unsupported/omitted currency:** model evidence remains advisory, no account-currency priority fallback or default/suggestion confirmation; existing canonical/source-adapter unit coverage is positive. Full current-owner resolver/Save eligibility is later T019/T016 scope, not this parser.
