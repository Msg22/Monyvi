## Source-validated current behavior

**Real local Add writer exists, but no terminal Add recovery carrier:** `services/account-default-intent-service.ts` L53–104 prepares one original validated form, current owner/default snapshot, immutable command IDs and recorded ancestor action IDs, then dispatches the exact Add envelope through `createAccountDefaultFinancialCommandService`. `account-default-intent-command.ts` L28–40 includes captured `snapshot`, `dependencyActionIds`, account/child/effect IDs and frozen envelope, but these are **in-memory fields**; they are not all persisted in the public payload. `account-default-intent-plan.ts` L236–305 prepares a genuine account, optional BankDetails/senders, opening effect and prior-default clear under one Watermelon writer, with owner/snapshot/ID rechecks and physical postimage verification. Its returned `FinancialActionLinkedOperationPlan` does **not** supply `buildLocalRecoverySnapshot`, so `financial_action_groups.local_recovery_snapshot_json` is still null for Add roots. The common foundation's optional private snapshot path is Review-only, and the nine-key versioned carrier in `review-local-recovery` is explicitly Review-bound. We cannot assume the local Add prepared postimage, prior-default metadata and newer ownership/edit proof survive a cold restart.

**Zero-opening protected sync is blocked despite valid local/SQL contract:** `services/account-review-recovery-protected-push.ts` L49–133 already parses `account.create-default/v1` through the actual approved registry, binds each mutation to real dirty row and validates owner, default clear, child parents, and zero/nonzero exact effect count. Yet `services/sync/account-protected-fields.ts` L321–366 rejects any complete bundle for `envelope.accountGuards.length===0` (line 346). That is legal and *mandatory* for zero-opening Add, whose immutable payload has no financial effects, no guards, but actual account/children. The common collector's blanket guard check is the precise zero-opening failure; strict Review and old nonzero legacy bundles still require their own guards. The generic-protected-ID collector can identify the new Add row/children via exact account/action refs, but without a dispatchable complete bundle the generic path cannot safely ACK those refs; it must not fall back to ordinary LWW. The new A01/A02/A04 tests demand a real complete zero-effect Add bundle, exact once-only protected transport and no false effect row.

**Rejection conservatively refuses Add, but does not reconcile:** `services/financial-action-reconciliation-production.ts` L487–514 directs Review to its strict nine-key local compensation and old tuples to the old canonical account/effect reconciler. It expressly throws `financial_action_reconciliation_incomplete` for `root.kind==="create_with_default"`. This is correct fail-closed behavior today; it cannot count as successful Add compensation. `financial-action-sync-service.ts` L151–211 persists accepted/idempotent/stale/rejected RPC outcomes; `createFinancialActionPushCoordinator` L253–266 calls the supplied reconciler for rejected roots and emits `recover` when incomplete. In absence of a real Add adapter, a failed Add leaves its optimistic new account, bank/sender children, default clear and possibly opening effect physically present. Old generic inverse compensation must not mark it reconciled, recreate an unknown default or produce fabricated zero effects.

**Predecessor capture is only partly durable:** `account-default-intent-snapshot.ts` L98–135 detects creator actions for the complete actual active/default set at prepare time. `account-default-intent-command.ts` retains those dependencies in its in-memory prepared command, but Add's immutable cloud payload intentionally has no `dependencyActionIds`, and the current local root has no private Add snapshot carrier. `account-review-default-predecessors.ts` L120–249 currently rederives owned creator dependencies from on-device genuine immutable roots and guards the protected push against pending/rejected/unowned predecessors, including a reread after awaits. This is meaningful current protection; it does not by itself prove restart-safe dependency intent after a local root/creator has been pruned or its account has been replaced. The A13–A15 tests exercise actual Add A→B prepared/committed SQLite actions, no second RPC before predecessor acceptance, rejected predecessor refusal after adapter clone, exact unchanged action bytes, and owner switching.

**Canonical outcome insufficiency:** Add's cloud tuple includes exact `expectedDefaultSnapshot`, account/child creates, optional prior-default clear and opening effect. A rejected/stale server outcome can include `canonicalAbsentAccountIds` and `canonicalAccounts` for financially guarded accounts. For **zero opening**, there are intentionally zero financial guards/effects and often no canonical account snapshot. Neither immutable public payload nor those outcome fields describe a verified *current owned default identity/set* after a competing server-side default change. The local prior default's prepared physical postimage and all child/effect created hashes also are not available from the existing Review-only private carrier. A failed Add cannot safely decide after restart whether to restore prior default A or preserve a newer user choice B, and cannot prove it is removing only *its* created child rows. Any recovery that blindly inverts `isDefault` or deletes account/child IDs from the payload alone is unsafe. This missing evidence is not fixed by adding private bytes to `payloadJson/outcomeJson` (forbidden cloud leak).
